# A3.6f — Overall Student Panel Investigation

## Scope

This is an investigation-only note for the Admin Dashboard Overall Student Panel, Quick Assign completion metrics, and Activity panel. It documents current behavior, likely root causes, and recommended fix order. No runtime behavior is changed by this PR.

## 1. Current Overall completion calculation

The Admin Dashboard API loads `student_progress` rows filtered to `app_id = "regents-algebra"` and `course_id = "algebra1"` for visible students. For each student, it groups those rows by `user_id` and calculates completion as `averagePercent(studentProgress.map((row) => toNumber(row.completion_percent)))`.

That value is exposed in two places:

- `studentsPayload[*].completionPercent` for the students table.
- `studentDetails[studentId].overallCompletion` for the Overall Student Panel.

The frontend displays `studentDetails[studentId].overallCompletion` in the Overall panel `Completion` card.

## 2. Root cause of incorrect Overall completion

Overall completion is currently an average over only the existing `student_progress` rows for the student. Missing sections are not included as 0%, and assignment rows are not used as the denominator.

As a result, a student who has a small number of `student_progress` rows can show 100% if every existing progress row is 100%, even if the student has no visible attempts or progress in most chapters. This metric answers “average completion among sections that have progress rows,” not “completion across assigned work” or “completion across the Algebra 1 course.”

The current calculation is not based on:

- assigned sections as the denominator,
- assignment recipients as the denominator,
- grouped assignment coverage,
- direct `question_attempts` coverage,
- all Algebra 1 sections.

It is based on existing `student_progress.completion_percent` rows only.

Recommended target definition: for the Overall Student Panel, completion should be explicitly defined as either assigned-work completion or course completion. Given the panel sits next to assignment-related cards, the least surprising metric is assigned-work learning progress: average section completion across active assigned sections for that student, treating assigned sections without progress as 0%. If a separate course-wide progress metric is desired, it should average across all Algebra 1 sections, also treating missing progress as 0%, and be labeled accordingly.

## 3. Current Assigned Work calculation

The Admin Dashboard API loads assignment rows, filters them to Regents section assignments, then loads `assignment_recipients` for those assignment ids. For each student, `assignedWorkCount` is currently `recipientsByStudent.get(student.id)?.length ?? 0`.

That value is exposed in:

- `studentsPayload[*].assignedWorkCount`,
- `studentDetails[studentId].assignedWorkCount`.

The frontend renders the detail value in the Overall Student Panel as `Assigned work`.

## 4. Root cause of incorrect Assigned Work counts

`assignedWorkCount` counts recipient rows, not grouped assignments or chapters. Because the assignment creation workflow creates one `assignments` row per section and one `assignment_recipients` row per student per section, the Overall panel card effectively counts section-level recipient rows.

This duplicates the Quick Assign panel’s more explicit “Assigned Chapters” and “Assigned Sections” concepts, while the generic `Assigned work` label suggests a higher-level assignment count. The count is also not deduplicated by grouped assignment, chapter, or assignment batch.

Recommended target definition: replace or relabel this card. Options:

1. Show `Assigned Sections` and keep the current recipient-row denominator, but label it accurately.
2. Show `Assigned Assignments` by counting grouped assignment bundles for the student.
3. Show both `Assigned Chapters` and `Assigned Sections` only in Quick Assign and remove the ambiguous Overall-panel card.

## 5. Current Quick Assign completion calculation

The Quick Assign student API loads active Quick Assign assignment rows for a student from `assignments` joined to `assignment_recipients`, then gathers `student_progress` rows for the assigned section ids. Each section’s `completionPercent` is populated directly from `student_progress.completion_percent` when a matching progress row exists.

Chapter completion is then calculated as the rounded average of the non-null section assignment completion values in that chapter. The overall Quick Assign completion metric is calculated as the rounded average of non-null assignment completion values across active Quick Assign section assignments.

`question_attempts` are used to count attempts and calculate accuracy, but not completion.

## 6. Root cause of incorrect Quick Assign completion

Quick Assign chapter completion has the same denominator problem as the Overall panel: sections without `student_progress` rows are excluded from the average instead of counted as 0%. If Chapter 1 has a single assigned section with a stale or otherwise existing 100% `student_progress` row, the chapter displays 100% even if Attempt History does not show recent or visible Chapter 1 work.

The metric is learning progress derived from `student_progress` for assigned sections, not assignment existence alone. However, because the average only includes sections with non-null progress rows, it can behave like “average completion for sections that have any recorded progress” instead of “completion across assigned chapter sections.”

Recommended target definition: Quick Assign chapter completion should average every active assigned section in the chapter, using `student_progress.completion_percent` where present and 0% for assigned sections with no progress. If the intended metric is assignment coverage, that should be a separate label such as “Sections assigned,” not “completion.”

## 7. Current Activity implementation

The Overall panel currently displays the heading `Recent Activity` and renders `detail.recentActivity` with `ActivityList`.

The API builds each student’s `recentActivity` from two sources:

- assignment recipient rows, using the assignment title, recipient status, section title, and `assigned_at` timestamp;
- `student_progress` rows, using section title, completion percent, and `last_active_at` timestamp.

The API separately builds `recentQuestionAttempts` from `question_attempts`, and the frontend displays those in the Attempt History panel rather than in the Overall panel’s `Recent Activity` list. The whole-school activity payload later combines student `recentActivity` with attempt-derived activity, but the single-student Overall panel does not use that combined list.

`AdminDashboardActivity` does not include `assignmentId`, grouped assignment id, section assignment id, section ids, or a route/action target. `ActivityList` renders static list items with no click handler.

## 8. Recommended Activity redesign

Rename the panel heading from `Recent Activity` to `Activity` and make the metric intentionally assignment-focused.

Recommended behavior:

- Show the student’s assignment activity history, ordered by meaningful event time.
- Include enough identifiers in the API payload to make assignment entries actionable:
  - section assignment id,
  - grouped assignment id or group key,
  - assignment title,
  - section id/title,
  - recipient status,
  - assigned/completed/archived timestamps,
  - per-student progress and attempt summary for that assignment section.
- Render assignment entries as buttons or links.
- On click, open the existing Admin Dashboard assignment summary context for that student if possible.

The Admin Dashboard payload already includes assignment summaries in `assignments[*].sectionAssignments[*].recipients[*]`, including per-recipient completion, accuracy, progress/attempt flags, and section assignment ids. However, the current activity item does not carry ids that connect it back to those summaries. Supporting clickable assignment activity primarily requires augmenting `AdminDashboardActivity` with assignment identifiers and adding a frontend selection handler that opens the matching assignment summary or a student-filtered summary view.

## 9. Files affected for a future implementation

Likely files for future fixes:

- `app/api/admin/org-dashboard/route.ts`
  - Rework Overall completion denominator.
  - Rework assigned work semantics.
  - Add assignment identifiers and richer metadata to student activity rows.
- `src/lib/admin/orgDashboard.ts`
  - Update dashboard types for new metrics/activity fields.
- `app/admin/page.tsx`
  - Rename `Recent Activity` to `Activity`.
  - Update card labels/metrics.
  - Add clickable assignment activity behavior.
- `app/api/admin/quick-assign/students/[studentUserId]/route.ts`
  - Rework Quick Assign section/chapter/overall completion denominator.

## 10. Recommended implementation order

1. Confirm product definitions for Overall completion: assigned-work completion vs course-wide completion.
2. Fix Quick Assign completion denominator first, because it has the clearest active-assigned-section scope.
3. Fix Overall completion using the approved denominator and label.
4. Rename or replace `Assigned work` so it no longer ambiguously counts section-recipient rows.
5. Extend activity payload types with assignment identifiers and summary metadata.
6. Rename the panel to `Activity` and make assignment entries clickable.
7. Add regression checks for students with assigned sections that have no `student_progress` rows and students with only a subset of 100% progress rows.
